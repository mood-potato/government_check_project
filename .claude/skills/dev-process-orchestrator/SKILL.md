# Dev Process Orchestrator

소프트웨어 개발 프로세스 7단계를 조율한다. 각 단계는 독립적으로 실행 가능하지만, 오케스트레이터가 전체 흐름을 관리한다.

## 실행 모드: 서브 에이전트

각 단계는 독립적이므로 서브 에이전트 패턴을 사용한다. 단계 간 팀 통신 불필요, 산출물은 파일 기반으로 전달한다.

---

## Phase 0: 컨텍스트 확인

시작 시 항상 먼저 확인한다:

1. `_workspace/` 디렉토리가 있는가?
   - **없음** → 초기 실행
   - **있음 + 사용자가 특정 단계 재실행 요청** → 부분 재실행 (해당 에이전트만)
   - **있음 + 새 기능 작업** → 새 실행 (`_workspace/`를 `_workspace_prev/`로 이동)

2. 사용자가 어느 단계에 있는지 파악:
   - 명시적으로 말했으면 해당 단계로 바로 이동
   - 모호하면 현재 단계를 물어본다

---

## 7단계 프로세스

```
1. 플로우 생성  →  2. 플로우 검토  →  3. 피쳐 기획 생성  →  4. 피쳐 기획 검토  →  5. 설계  →  6. 개발  →  7. 검증
   flow-create      flow-review       feature-planning      feature-validation    schema-design  dev-guide   code-review-process
```

각 단계는 독립 실행 가능. 사용자가 원하는 단계만 실행해도 된다.

---

## 단계별 실행

### 1단계: 플로우 생성

`flow-create` 스킬 실행.

**입력:** 기능 아이디어 또는 요구사항 설명
**출력:** Happy Path + 주요 분기 + 외부 의존성 포함한 서비스 플로우 초안
**저장:** `_workspace/01_flow_create.md`

**다음 단계 전환 조건:**
- 사용자가 플로우 초안을 확인하고 다음 진행 결정

---

### 2단계: 플로우 검토

`flow-review` 스킬 실행.

**입력:** 1단계 산출물 또는 사용자가 직접 작성한 플로우
**출력:** 누락 케이스 목록 (블로킹/주요/선택)
**저장:** `_workspace/02_flow_review.md`

**다음 단계 전환 조건:**
- 블로킹 이슈가 해소되었거나, 사용자가 다음 진행을 명시적으로 결정

---

### 3단계: 피쳐 기획 생성

`feature-planning` 스킬 실행.

**입력:** 2단계 산출물 (flow-review 결과)
**출력:** 케이스 목록 (Happy/Edge/Error) + 요구사항 초안 (flow-review 블로킹 이슈 반영)
**저장:** `_workspace/03_feature_planning.md`

**다음 단계 전환 조건:**
- 사용자가 케이스 목록과 요구사항 초안을 확인하고 다음 진행 결정

---

### 4단계: 피쳐 기획 검토

`feature-validation` 스킬 실행.

**입력:** 3단계 산출물 또는 사용자가 직접 작성한 케이스 목록/요구사항
**출력:** 누락 케이스 + 모호한 요구사항 목록
**저장:** `_workspace/04_feature_validation.md`

**다음 단계 전환 조건:**
- 주요 모호 항목이 해소되었거나, 사용자 결정

---

### 5단계: 설계 — 스키마 + API

`schema-design` 스킬 실행.

**입력:** 요구사항 (4단계 산출물 참조 가능)
**출력:** DB 스키마 + RLS 정책 + API 명세
**저장:** `_workspace/05_schema_design.md`

**다음 단계 전환 조건:**
- 과설계 여부 확인 완료, RLS 정책 두 페르소나 커버 확인

---

### 6단계: 개발 — 수직 슬라이싱

`dev-guide` 스킬 실행.

**입력:** 태스크 1개 (S~M 크기)
**출력:** 구현 완료 보고 + 범위 밖 발견 사항
**저장:** `_workspace/06_dev_log.md` (태스크마다 append)

**반복 실행:** 태스크가 완료될 때마다 다음 태스크로 반복

---

### 7단계: 검증 — 코드 리뷰 + 버그 분석

`code-review-process` 스킬 실행.

**입력:** 리뷰할 코드 또는 에러 메시지
**출력:** 블로킹/선택 이슈 목록 또는 가설 3개
**저장:** `_workspace/07_review_log.md`

---

## 공통 원칙 (모든 단계 적용)

이 원칙들은 각 단계 스킬에도 포함되어 있지만, 오케스트레이터가 전체적으로 보장한다:

| 원칙 | 동작 |
|------|------|
| **가정 드러내기** | 각 단계 시작 전 가정 목록 출력 → 사용자 확인 후 진행 |
| **범위 고정** | 현재 단계 스킬만 실행. 다른 단계 작업은 하지 않음 |
| **증거 요구** | "완료" 보고 시 "어떤 케이스를 어떻게 확인했는지" 포함 |
| **막히면 멈춤** | 불확실하면 추측 진행 대신 사용자 확인 요청 |

---

## 에러 핸들링

| 상황 | 처리 |
|------|------|
| 사용자가 단계를 건너뛰려 함 | 허용. 각 단계는 독립 실행 가능 |
| 이전 단계 산출물 없이 다음 단계 요청 | 산출물 없이 진행 가능하지만 "1단계 산출물이 없습니다. 직접 입력을 주시거나 건너뛰겠습니다"라고 알림 |
| 태스크가 L 크기 | `dev-guide` 스킬 위임 전 분해 안내 |
| 특정 에이전트 실패 | 해당 단계 결과 없이 진행, 최종 보고에 누락 명시 |

## 저장 연동

각 단계 완료 후 사용자가 원하면 `notion-save` 스킬 실행:
- Notion 페이지에 단계별 산출물 저장
- CLAUDE.md에 컨텍스트 포인터 추가

## 테스트 시나리오

**정상 흐름 (처음부터):**
"새 기능 기획부터 시작하고 싶어. [기능 설명]"
→ flow-create 스킬 트리거 → 가정 목록 출력 → 사용자 확인 → 플로우 초안 출력
→ flow-review 스킬 트리거 → 누락 케이스 목록 출력
→ feature-planning 스킬 트리거 → 케이스 목록 + 요구사항 초안 출력
→ feature-validation 스킬 트리거 → 모호 항목 지적

**정상 흐름 (중간 진입):**
"플로우는 있는데 케이스 목록으로 넘어가고 싶어. [플로우 검토 결과]"
→ feature-planning 스킬 트리거 → 케이스 목록 + 요구사항 초안 출력

**에러 흐름:**
"요구사항 검토해줘 [내용 없이]"
→ "검토할 요구사항 문서나 케이스 목록을 붙여넣어 주세요." 응답 후 대기
