# Code Review Process — 검증 단계

## 두 가지 모드

- **코드 리뷰 모드**: 구현 완료된 코드 검토
- **버그 분석 모드**: 에러 메시지 + 관련 코드가 있을 때

---

## 코드 리뷰 모드

### Step 1: 가정 드러내기

```
리뷰를 시작하기 전에 가정하고 있는 것들을 나열합니다:
- 실행 환경: [파악한 내용]
- 데이터 규모: [파악한 내용]
- 기존 패턴: [파악한 내용]
확인해주시면 시작하겠습니다.
```

### Step 2: 5가지 기준 순서대로 검토

**① 동작 정확성**
- 명세대로 동작하는가
- 엣지 케이스 (빈 배열, null, 최대값) 처리
- 비동기 처리 순서가 맞는가
- 조건문 분기가 완전한가 (else 누락)

**② 가독성**
- 변수/함수명이 의도를 드러내는가
- 5초 이상 봐야 이해되는 로직이 있는가
- 주석이 필요한 부분에 주석이 있는가

**③ 기존 패턴 일치**
- 코드베이스의 컨벤션(네이밍, 파일 구조)을 따르는가
- 같은 기능의 기존 구현과 스타일이 일치하는가

**④ 보안**
- 사용자 입력을 직접 쿼리에 넣는가 (SQL injection)
- 권한 확인이 누락된 엔드포인트가 있는가
- 민감 정보가 로그에 출력되는가
- XSS 취약점 (React에서 dangerouslySetInnerHTML 등)

**⑤ 성능**
- N+1 쿼리 패턴 (루프 안에서 DB 쿼리)
- 불필요한 전체 리스트 조회 후 필터링
- 메모리에 대용량 데이터를 한번에 로드

### Step 3: 출력

```markdown
## 가정

## 리뷰 결과

### 블로킹 이슈
(서비스 불가, 데이터 손실, 보안 위협 — 반드시 수정)
- [기준] `파일:라인`: [문제] → [수정 방향]

### 선택 사항
(품질 개선, 가독성, 성능 최적화)
- [기준] `파일:라인`: [문제] → [개선 방향]

## 확인한 케이스
- [케이스]: [확인 방법과 결과]
```

**"됐을 것 같다"는 결론 금지.** 불확실하면 "이 부분은 [조건]이 성립할 때 문제가 생길 수 있습니다. 확인이 필요합니다."로 표현한다.

## 버그 분석 모드

### Step 1: 에러 정보 수집

에러 메시지와 코드가 모두 있으면 바로 진행. 하나라도 없으면 요청한다.

### Step 2: 가설 3개 생성

단일 원인으로 단정하지 않는다. 반드시 3개의 독립적인 가설을 생성한다.

**가설 생성 기준:**
- 가설 간 중복 없이 서로 다른 원인을 제시
- 각 가설은 구체적인 확인 방법을 가짐
- 가장 가능성 높은 순서로 정렬

### Step 3: 출력

```markdown
## 원인 가설

### 가설 1: [원인 제목]
근거: [왜 이것이 원인일 수 있는지]
확인 방법:
1. [구체적 확인 절차]
2. [확인 절차]

### 가설 2: [원인 제목]
근거: [왜 이것이 원인일 수 있는지]
확인 방법:
1. [구체적 확인 절차]

### 가설 3: [원인 제목]
근거: [왜 이것이 원인일 수 있는지]
확인 방법:
1. [구체적 확인 절차]

## 우선 확인 순서
1. 가설 [번호] — [이유: 가장 빠르게 확인 가능 / 가장 가능성 높음]
2. 가설 [번호]
3. 가설 [번호]
```

사용자가 확인 결과를 알려주면, 해당 가설 기반으로 수정 방향을 제시한다.
