# Feature Planning — 피쳐 기획 초안 생성

## 목적

feature-validation이 검토할 케이스 목록과 요구사항 초안을 만드는 것이다. flow-review의 발견 사항을 반영하여 초안을 구체화한다.

---

## 실행 순서

### Step 1: 입력 확인

| 상황 | 처리 |
|------|------|
| flow-review 산출물 있음 | 누락 케이스 목록을 반영하여 생성 |
| flow-review 산출물 없음 | 기능 설명만으로 생성하되 "flow-review 결과 없이 생성합니다"라고 명시 |

### Step 2: 케이스 목록 생성

flow-review에서 발견된 **블로킹** 이슈는 반드시 Error Case에 포함한다. **주요** 이슈는 Edge Case 또는 Error Case에 포함한다.

| 구분 | 기준 |
|------|------|
| Happy Path | 정상 흐름의 각 단계 (입력 → 처리 → 결과) |
| Edge Case | 경계값, 동시성, 순서 의존성, 빈 상태 |
| Error Case | 외부 의존성 실패, 권한 오류, 데이터 오류, 타임아웃 |

### Step 3: 요구사항 초안 생성

각 케이스의 처리 방식을 요구사항으로 작성한다. 두 가지 기준을 지킨다:

- **측정 가능한 표현** — "빠르게"가 아니라 "p95 기준 2초 이내"
- **Scope 명확히** — 무엇이 포함되고 무엇이 제외되는지 명시

### Step 4: 출력

```markdown
## 케이스 목록: [기능명]

> flow-review 반영: 블로킹 N건, 주요 N건 포함됨
> (flow-review 없이 생성한 경우 이 줄 대신 "flow-review 결과 없이 생성"으로 표시)

### Happy Path
- [ ] [케이스 설명]
- [ ] [케이스 설명]

### Edge Case
- [ ] [케이스 설명]
- [ ] [케이스 설명]

### Error Case
- [ ] [케이스 설명]  ← flow-review 블로킹 이슈
- [ ] [케이스 설명]

---

## 요구사항 초안

### In Scope
- [요구사항] — [근거 케이스]

### Out of Scope
- [명시적으로 제외하는 항목과 이유]

### 미결 질문
- [scope 결정을 위해 사용자 확인이 필요한 항목]
```

---

## 핵심 원칙

**초안이다.** feature-validation이 지적할 여지를 남겨두는 것이 정상이다. 완벽한 목록을 만들려고 하지 않는다.

**멈추는 기준:** 기능 설명이 없고 flow-review 산출물도 없으면 → "기능 설명이나 flow-review 결과를 먼저 공유해 주세요."
