# Schema Design — 설계 단계

## 실행 순서

### Step 1: 가정 드러내기

스키마를 작성하기 **전에** 반드시 먼저 출력한다:

```
스키마 설계를 시작하기 전에 가정하고 있는 것들을 나열합니다:
- 사용자 규모: [예상치]
- 페르소나: [파악한 역할들]
- 기술 스택: [확인된 것]
- 기존 스키마: [있음/없음]
확인해주시면 설계를 시작하겠습니다.
```

### Step 2: 과설계 필터링

요구사항을 읽고, 현재 태스크에서 실제로 필요한 필드만 식별한다.

**필드 포함 기준:**
- 현재 요구사항에서 직접 읽거나 쓰는 필드 → 포함
- "나중에 쓸 수도 있어서" 추가하는 필드 → 제외
- 통계나 분석용으로 추후 필요할 수 있는 필드 → 제외 (별도 마이그레이션으로)

### Step 3: 스키마 작성

**테이블 구조:**
```markdown
### {table_name}
| 필드명 | 타입 | 필수 | 기본값 | 설명 |
|-------|------|------|--------|------|
| id    | uuid | Y    | gen_random_uuid() | PK |
| created_at | timestamptz | Y | now() | 생성일 |

**인덱스:**
- [필드명]: [인덱스 이유]

**제약 조건:**
- [제약 내용]
```

### Step 4: RLS 정책 작성

두 페르소나를 모두 커버한다. 페르소나가 하나뿐이어도 미래 확장성을 위해 역할 분리를 명시한다.

```markdown
### RLS 정책: {table_name}

| 작업   | 조건 | 허용 역할 |
|--------|------|---------|
| SELECT | [조건] | [역할] |
| INSERT | [조건] | [역할] |
| UPDATE | [조건] | [역할] |
| DELETE | [조건] | [역할] |
```

### Step 5: API 명세 작성 (요청 시)

```markdown
### {METHOD} /api/{endpoint}

**설명:** [한 줄 설명]
**권한:** [필요 역할]

**요청 바디:**
```json
{
  "field": "type // 설명"
}
```

**응답 (200):**
```json
{
  "field": "type // 설명"
}
```

**에러 케이스:**
- 400: [조건]
- 403: [조건]
- 404: [조건]
```

### Step 6: 범위 밖 발견 사항 기록

설계 중 발견한 기존 코드 문제나 아키텍처 이슈는 수정하지 않고 별도로 기록한다.

## 출력 완료 후 체크

스키마 출력 후 반드시 두 가지를 사용자에게 확인한다:
1. "현재 태스크에서 실제로 필요한 필드만 있나요? 제거할 필드가 있으면 알려주세요."
2. "RLS 정책이 [페르소나 A]와 [페르소나 B]를 모두 고려하고 있나요?"
