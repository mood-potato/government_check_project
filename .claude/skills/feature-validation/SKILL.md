# Feature Validation — 피쳐 기획 단계

## 두 가지 모드

사용자 입력에 따라 모드를 선택한다:
- **케이스 검토 모드**: 케이스 목록이 있을 때
- **요구사항 검토 모드**: 요구사항 문서가 있을 때
- 둘 다 있으면 케이스 검토 → 요구사항 검토 순으로 진행

---

## 케이스 검토 모드

### Step 1: 가정 드러내기
검토 전 가정 목록 출력 → 사용자 확인 → 진행

### Step 2: 3-Layer 검토

| Layer | 확인 내용 |
|-------|---------|
| Happy Path | 정상 흐름에서 빠진 단계가 있는가 |
| Edge Case | 경계값, 동시성, 순서 의존성이 누락되었는가 |
| Error Case | 외부 의존성 실패, 권한 오류, 데이터 오류가 누락되었는가 |

**Edge Case 체크리스트:**
- 빈 입력 / null / 최대값 초과
- 동시에 두 사용자가 같은 리소스 수정
- 이미 완료된 작업을 다시 실행
- 긴 텍스트, 특수문자, 다국어 입력

**Error Case 체크리스트:**
- 외부 API 타임아웃 / 5xx
- DB 연결 실패
- 파일 업로드 크기 초과 / 형식 불일치
- 권한 없는 사용자의 접근

### Step 3: 출력

```markdown
## Happy Path 누락
- [케이스]: [이유]

## Edge Case 누락
- [케이스]: [이유]

## Error Case 누락
- [케이스]: [이유]
```

## 요구사항 검토 모드

### Step 1: 가정 드러내기
검토 전 가정 목록 출력 → 사용자 확인 → 진행

### Step 2: 3가지 기준 검토

**① 모호한 표현**
"적절히", "빠르게", "사용자 친화적" 등 해석이 다를 수 있는 표현을 모두 찾는다.

**② 측정 불가 성공 기준**
수치나 조건으로 표현할 수 없는 기준을 찾는다.
예: "성능이 좋아야 한다" → "p95 기준 2초 이내"로 바꿀 수 있는지 확인

**③ Out of scope 불명확**
명시하지 않아서 scope 안인지 밖인지 판단 불가능한 항목을 찾는다.

### Step 3: 출력

```markdown
## 모호한 표현
- 위치: "[원문]"
  → 제안: [측정 가능한 표현]

## 측정 불가 성공 기준
- 위치: "[원문]"
  → 문제: [왜 측정 불가인지]
  → 제안: [수치/조건으로 표현한 대안]

## Out of scope 불명확
- 항목: [무엇이 불명확한지]
  → 질문: [Scope 안인지 밖인지 결정하기 위해 필요한 정보]
```

---

## 핵심 원칙

**직접 만들지 않는다.** 케이스 목록이나 요구사항을 처음부터 작성해달라는 요청은 받지 않는다. 사용자가 작성한 것을 검토하는 역할이다. 직접 만들면 일반적인 목록이 나와서 프로젝트 특수성이 빠지기 때문이다.
